# Security checklist

Every item from the plan's "Security checklist (v2)", plus the usual web-app checks, with what implements it and the tests that prove it. Checked on 26 Nov 2026 against `dev` at `76faf5e` plus this change.

Result: **no permission bypass, no injection found.** Six gaps were found and fixed in this change (marked **Fixed**); four items are recorded as known limits.

## Requests

| Item | Status | Where | Tests |
| --- | --- | --- | --- |
| CSRF token on every state-changing cookie request, besides SameSite=Lax | Pass | Checked twice. A layer in front of every route (`require_csrf`, `src/auth/mod.rs`) refuses any POST, PUT, PATCH or DELETE that carries a session cookie without the matching `x-csrf-token`, before any handler runs; only requests with an `Authorization` header and the signed unsubscribe and command-line sign-in endpoints skip it. Each handler also calls `check_csrf` (`Project::writing`, `Board::writing`, `CompanyOwner::writing`, `SuperAdmin::writing` or directly). Bearer requests never fall back to the cookie (`src/tenant.rs`). | `every_write_route_refuses_a_cookie_request_without_the_csrf_token` (finds every write route in `src/` and sends each one without the token), `admin_writes_need_the_csrf_token_and_leave_no_trace_without_it`, `project_changes_need_the_csrf_token`, `a_bearer_header_never_falls_back_to_the_cookie_and_cookies_still_need_csrf` |
| Exempt endpoints are safe | Pass | OAuth start and callback are GETs bound to a sealed `state` cookie; unsubscribe POST needs an HMAC-sealed token and only turns emails off; `POST /cli/device` grants nothing and `POST /cli/token` needs the 256-bit device code; approving a code needs a session and CSRF; the WebSocket upgrade checks `Origin`. | `a_callback_without_the_matching_state_is_rejected`, `one_click_unsubscribe_turns_notification_emails_off`, `the_device_code_flow_hands_out_one_token_after_approval`, `only_the_app_itself_may_open_a_live_connection` |
| Rate limits: API per token | Pass | 120 requests a minute per token, then 429 with `Retry-After` (`src/api/tokens.rs`). | `a_token_over_its_rate_limit_gets_429`, `the_rate_limit_resets_each_minute` |
| Rate limits: sign-in per address | **Fixed** | Command-line sign-in was already limited (10 a minute per address). The proxy adds the last entry itself, so a visitor cannot choose it as long as the setting matches the proxy in front; anything that is not an IP address counts as unknown. | `google_sign_in_is_limited_per_address_not_for_everyone`, `starting_sign_ins_is_limited_per_address_not_for_everyone`, `the_client_address_is_the_last_hop_the_proxy_added`, `the_client_address_header_can_be_chosen`, web `explains the busy error` |
| Every handler checks project role and board access on the server | Pass | `Company` (membership, active company, token limits), `Project::load` (role), `Board::load` (restricted boards, closed boards). Child ids are always looked up inside their board. Search, My cards, notifications and webhooks filter with the same visibility rule; the board WebSocket re-checks access on every change. | `people_not_on_a_restricted_board_cannot_see_it_even_by_address`, `every_role_gets_exactly_the_access_the_plan_gives_it`, `observers_cannot_change_anything`, `attachments_follow_the_card_access_rules`, `a_project_limited_token_cannot_read_another_project`, `the_live_connection_follows_the_same_access_rules`, `owners_get_signed_events_only_from_boards_they_can_see` |

## Secrets and people

| Item | Status | Where | Tests |
| --- | --- | --- | --- |
| Tokens stored only as hashes and shown once | Pass | Sessions, personal tokens, company tokens and device codes are stored as SHA-256; the secret is in the create response only. Unsubscribe links are HMAC-sealed and never stored. | `tokens_are_stored_as_hashes_shown_once_and_revocable`, `the_device_code_flow_hands_out_one_token_after_approval` |
| Webhook secrets can be rotated | **Fixed** | `POST /api/v1/c/{company}/webhooks/{hook}/secret` (CSRF) gives the webhook a new salt and returns the new secret once; Integrations → Webhooks → Deliveries → **New secret**. Only the owner who added the webhook can do it, so another owner cannot take the secret of a webhook for projects they are not in. Deliveries sent from then on carry the new signature; a batch already being sent may still carry the old one. The rotation is written to the audit log. | `owners_can_rotate_a_signing_secret_and_the_old_one_stops_verifying`, web `replaces the signing secret and shows the new one once` |
| Email-to-board secrets can be rotated | Not built | Email-to-board does not exist yet. | – |
| Secrets never in the repository, logs or chat | Pass | `scripts/checks.py secrets` blocks keys and filled secret settings; config secrets print as `[hidden]`; no log line prints a token, cookie, password or webhook secret. | `checks.py` tests in `tests/ci/test_checks.sh`, `debug_output_hides_secrets` |
| Invites expire | **Fixed** | An invite now lasts 7 days (`expires_at`, set by a database trigger in control migration 0009, so every way of creating an invite gets it). An expired invite no longer lets anyone in or join a company; signing in with only an expired invite is refused with "invitation expired", and the address can be invited again at once. Invites that were already pending when the change was deployed got 7 days from then. | `invites_last_seven_days_and_an_expired_one_can_be_sent_again`, `an_expired_invite_is_refused_with_its_own_reason_and_can_be_sent_again`, web `explains an expired invitation` |
| Board templates do not carry cards out of restricted boards | **Fixed** | Templates are visible to the whole company, so a template saved from a restricted board keeps only its lists, labels and custom fields (owner decision); its cards are left out, the board is checked in the same transaction as the copy, and the save dialog and the confirmation say so. The template's name, list titles, label names and field names stay visible to the company (see Known limits). | `a_template_from_a_restricted_board_keeps_its_structure_but_no_cards` |
| Removing a person ends their access at once | Pass | Every request re-checks company membership, so sessions and personal tokens stop at once; live connections re-check on every change and every 25 seconds and close. Their name stays on past activity. | `people_who_lose_access_lose_it_through_their_tokens`, `leaving_the_company_ends_project_access_even_after_coming_back`, `signing_out_or_a_suspended_company_closes_the_live_connection`, `admins_cannot_lock_themselves_out_and_disabling_ends_sessions` |
| Company tokens end for good when their maker stops being an owner | **Fixed** | They were only paused while the maker was not an owner and worked again if the person was made an owner again. Now stepping down to member, or leaving the company, revokes them, and the audit log records how many were revoked and why. The tokens are revoked before the role change is saved, so a failure cannot leave a demoted owner with live tokens, and again after it, so a token made in between is caught too. | `company_tokens_stay_revoked_after_their_maker_is_made_an_owner_again` |

## Known limits

- **The client address setting must match the proxy.** If `TAZKO_CLIENT_IP_HEADER` names a header the proxy in front does not set, visitors can send that header themselves and each gets a sign-in bucket of their own. The demo behind its tunnel needs `TAZKO_CLIENT_IP_HEADER=x-forwarded-for`.
- **Templates from restricted boards** still show their name, list titles, label names and field names to the whole company; only cards are left out.
- **Templates saved before this change** from a restricted board still contain its cards, and so do copies already offered to every company; delete and save them again if that matters.
